## 1. Summary

Three intertwined changes to CLI logging, all shipping in PR #575:

1. **Stream routing fix** — align with POSIX/GNU: stdout = command data, stderr = diagnostics. Today [`BuildStreams`](src/CLI/Program.cs#L203-L253) sends warning/info/verbose/debug to stdout, polluting `--output json` pipelines. Every peer CLI (Azure CLI Python, Az PowerShell, AWS CLI, git, kubectl, docker, terraform) puts diagnostics on stderr.
2. **Default log level → `warn`** (was `error`). Matches Azure CLI Python and Az PowerShell defaults; surfaces warnings that are currently silently swallowed (e.g. [`LoginProcessor.cs` L419, L428](src/Extensions/Login/Processors/LoginProcessor.cs#L419-L428)).
3. **Extension-load debug tracing** — per-extension load rows + aggregate summary table on [`ExtensionLoader`](src/CLI/AssemblyLoading/ExtensionLoader.cs), modelled on [`azure-cli/src/azure-cli-core/azure/cli/core/__init__.py` L232-L235, L680-L688](https://github.com/Azure/azure-cli/blob/dev/src/azure-cli-core/azure/cli/core/__init__.py#L232). All at `Debug`; emitted only under `--debug` or `core.logging.level=debug`.

## 2. Decision Registry

Succinct "why" for each committed decision. All resolved 2026-07-21.

| #       | Decision                                                                                     | Rationale                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D1**  | Default log level: `warn` (was `error`)                                                      | Azure-family peer symmetry. Azure CLI Python console default is `Warning` ([azlogging.py](https://github.com/Azure/azure-cli/blob/dev/src/azure-cli-core/azure/cli/core/azlogging.py) header docstring); Az PowerShell effective baseline is `Warning + Error` ([about_preference_variables](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_preference_variables?view=powershell-7.6)). AWS CLI is `Error`-only but has no warn tier at all — different data model, not a competing default. `info`-as-default rejected: no cited peer defaults console to Info, and would require call-site retriage (see D8).<br><br>**PS-side effect (intentional):** the config is shared, so PS cmdlets read `warn` too. Under `error`, [`CmdletOutputStreamsFactory.WriteWarning` L86-L94](src/PS/Common/CmdletOutputStreamsFactory.cs#L86-L94) silences warnings before they reach the PS host; under `warn` they flow through `cmdlet.WriteWarning(...)` and the PS host applies its own `$WarningPreference` (default `Continue` = shown). Info/Verbose/Debug behavior is unchanged (still gated at `warn`; per-invocation `-Verbose`/`-Debug` overrides still bypass the gate). Callers who want the old silence use `-WarningAction Ignore` — the PS-idiomatic escape hatch. Aligns with Az PowerShell convention. |
| **D2**  | Route Warning/Info/Verbose/Debug to **stderr**                                               | Industry standard. POSIX defines stderr as the "diagnostic output stream". [GNU Coding Standards §4.4](https://www.gnu.org/prep/standards/html_node/Errors.html): _"All error messages should be directed to stderr rather than stdout."_ Adopted by every peer CLI examined. Current stdout routing is a bug, not a philosophy.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

| **D10** | Harmonize diagnostic prefix to `LEVEL: message` (uppercase word, single colon, single space) | Three surfaces were emitting three different styles: [`BuildStreams`](src/CLI/Program.cs#L211-L251) mixed `[ERROR]` with `WARNING:`/`INFO:`/`VERBOSE:`/`DEBUG:`; [`ConsoleLoggingService`](src/Core/Core.Runtime/ConsoleLoggingService.cs) used all-bracketed `[ERROR]`/`[WARN]`/`[INFO]`/`[VERBOSE]`/`[DEBUG]`; [`AgentEventStyle`](Agent/Hosting/AgentEventStyle.cs#L91-L100) used `[ERROR]`/`[WARN]`. Chose `LEVEL:` because: (1) matches Azure CLI Python's `WARNING:` output and the Python `logging` default formatter (peer symmetry — same rationale as D1); (2) matches PS host's own default rendering of `cmdlet.WriteWarning("x")` — the CLI now looks the way PS users already see warnings; (3) human-facing CLI convention is `program: level: message`, log-aggregator convention is `[LEVEL]` — AzClips is a CLI; (4) full word `WARNING` not `WARN` matches Python level names and is self-explanatory. Applied uniformly across all levels, including `ERROR:` (was the odd bracketed one). Consolidated **now** because AzClips is pre-production and no downstream parser has locked in a style yet — later would be a breaking change. Also simplifies the TUI [`ClassifyLine`](TUI/services/ProcessService.cs) to one prefix per level.                                                                                           |

**PS terminology aside** (relevant to D1): the [about_logging_non-windows](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_logging_non-windows?view=powershell-7.6) quote about _"Informational logging to the Operational channel"_ describes PowerShell writing to the **OS event log / syslog** (telemetry-style), not console verbosity. Console verbosity in PS is governed by the `$*Preference` variables, which is the apples-to-apples comparison used in D1.

## 5. Follow-ups (out of this PR)

Separate issues / PRs to open once this one lands. Captured so we don't lose them.

- [ ] **Broader color audit / `ColorPolicy` abstraction.** This PR ships a minimal `ColorPolicy.ShouldEmitColor(...)` static (§3.1 item 4) applied at the eight `Console.ForegroundColor` sites in `Program.cs`, `ConsoleLoggingService.cs`, and `ConsoleOutputAdapter.cs`. Follow-up should audit color usage across `TUI/`, `Core.Agent/Hosting/`, and any other `Console.ForegroundColor` sites; and consider adopting [Spectre.Console](https://spectreconsole.net/) wholesale (which handles color decisions plus much more). **This work is expected to merge into the `ConsoleSink` follow-up below** — once `ConsoleSink` owns color decisions internally, the free-standing `ColorPolicy` static becomes an implementation detail of the sink and its callers stop passing `IsErrorRedirected`/`IsOutputRedirected` at each site.

- [ ] **Add a `Warn` value to `HistoryItemType` in the TUI.** Uncovered by §3.1 item 5 (2026-07-21): the TUI's [`HistoryItemType`](TUI/Models.cs#L11) has `User, Output, Error, Info, Success, ToolCall, Separator` but no `Warn`. This PR maps AzClips `WARNING:` lines to `HistoryItemType.Info` (dim gray `◇`), which understates severity. Follow-up: add `Warn` to the enum, a renderer case in [`HistoryRenderer.cs`](TUI/Rendering/HistoryRenderer.cs) (e.g. yellow `⚠`), and route the classifier's warning branch to it.

- [ ] **Deprecate and remove `ILoggingService.Log(string)`.** `Log` has zero production call sites (grep confirmed 2026-07-21; only reference is [`RendererLoggingServiceTests.cs` L67](Agent/tests/Core.Agent.Tests/RendererLoggingServiceTests.cs#L67)) and its semantics duplicate `Info` after D3. Removing it is a public-API break, so it needs its own PR with a proper deprecation path:
    1. Mark `Log` with `[Obsolete("Use Info instead. Log will be removed in a future release.", error: false)]` in [ILoggingService.cs](src/Core/Core.Abstractions/ILoggingService.cs#L14-L15).
    2. Remove the coverage test at [`RendererLoggingServiceTests.cs` L67](Agent/tests/Core.Agent.Tests/RendererLoggingServiceTests.cs#L67) or narrow it to only the levelled methods.
    3. In a later release, remove `Log` from the interface and from `ConsoleLoggingService`, `ScopedLoggingService`, `OutputStreamAdapter`, `NoOpLoggingService`, and `RendererLoggingService`.

- [ ] **Call-site severity retriage under an `info` default** (D8). Only worthwhile if we ever aim at `core.logging.level = info` as the baseline; would require demoting the `Info` sites (alias resolution, extension-load progress, `[TIMING]` traces, subscription lifecycle) to `Verbose`/`Debug` first.

- [ ] **`core.logging.stream` config knob** (`stdout` / `stderr` / `auto`). Useful only if users report a real need to revert to the pre-D2 stdout-for-everything behavior. Bug-report-driven; open only if warranted.
